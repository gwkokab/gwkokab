# Population Inference from Posterior Samples (Discrete Method)

## Introduction

The previous tutorial,
[Simulating a Gravitational-Wave Catalogue](./simulating_a_catalogue.md), produced a catalogue of
mock detections in `data/event_*.hdf5`, each carrying a set of posterior samples in
$(m_1, m_2, \chi_{1,z}, \chi_{2,z}, \epsilon)$. Here we take those samples and recover
the population hyperparameters

$$
\Lambda = \{\mathcal{R}_0, \alpha, \beta, m_{\mathrm{min}}, m_{\mathrm{max}},
\mu_{\chi_z}, \sigma_{\chi_z}, \sigma_{\epsilon}\}
$$

that generated them. Reading the
[Model Specification](./simulating_a_catalogue.md#model-specification) section of that tutorial
first is recommended, since the recovery model is set up with exactly the same flags.

We call this the **discrete** method because each event's likelihood is evaluated as a
Monte Carlo sum over its discrete posterior samples. The
[next tutorial](./inference_from_gaussian_summaries.md) replaces that sum with a multivariate normal
approximation and compares the two.

## The Hierarchical Likelihood

For an inhomogeneous Poisson process with rate density $\rho(\theta\mid\Lambda)$, $N$
detected events, and $M_n$ posterior samples $\theta_{n,k}$ for the $n$-th event drawn
under the parameter-estimation prior $\pi_n$, the log-likelihood is

$$
\ln\mathcal{L}(\Lambda) =
-\mu(\Lambda) + N\ln T_{\mathrm{obs}} +
\sum_{n=1}^{N}\ln\left[\frac{1}{M_n}
\sum_{k=1}^{M_n}\frac{\rho(\theta_{n,k}\mid\Lambda)}{\pi_n(\theta_{n,k})}\right]
$$

The first term is the expected number of detections from
[Detector Sensitivity](./simulating_a_catalogue.md#detector-sensitivity); the sum over $k$ is the
Monte Carlo estimate of the per-event marginal likelihood
$\int \mathcal{L}_n(\theta)\rho(\theta\mid\Lambda)\,\mathrm{d}\theta$.

That Monte Carlo estimate is the weak point of the method: as $\Lambda$ moves into a
region where only a handful of an event's samples carry appreciable weight, the estimate
becomes noisy and the sampler can be drawn towards spurious likelihood spikes. GWKokab
tracks the per-event variance of the estimator and can penalise samples whose variance
exceeds a threshold through `--variance-cut-threshold`. We do not use it in this example,
since 5000 samples per event over five parameters is comfortable, but it is worth
remembering when the number of samples per event is small.

## Loading the Data

Which files to read, and how, is described by a data loader configuration. Ours,
[`data_loader_cfg.json`](https://github.com/kokabsc/gwkokab/blob/main/docs/source/examples/ecc_plus_spin/data_loader_cfg.json),
is as short as it gets:

```json
{
    "regex": "../data/event_*.hdf5"
}
```

[`regex`](../../inference_io/discrete_pe_loader.md#regex) is a glob pattern; every file it
matches becomes one event. The path is relative to the directory the analysis is launched
from, and since we run each analysis inside its own sub-directory the pattern reaches one
level up.

Every other field has a default, and for this catalogue every default happens to be right
— which is why the file is one line long.
[`DiscretePELoader`](../../inference_io/discrete_pe_loader.md) documents all of them; the
ones a real catalogue is most likely to need are
[`default_datasets`](../../inference_io/discrete_pe_loader.md#default_datasets), naming
where in each HDF5 file the samples live,
[`parameter_aliases`](../../inference_io/discrete_pe_loader.md#parameter_aliases) for files
that use different column names, and
[`max_samples`](../../inference_io/discrete_pe_loader.md#max_samples) to trade accuracy for
memory.

One default does deserve a note here, because it is a statement about the data rather than
about the loader. `default_mass_prior`, `default_spin_prior` and `default_distance_prior`
describe the priors the original parameter-estimation run assumed — the $\pi_n$ of the
likelihood above — so that they can be divided back out. All three default to `null`,
meaning a flat reference prior, and that is exactly right here: our mock posteriors were
generated by perturbing the truth, and no PE prior was ever imposed. A real catalogue will
need all three set, and per-event overrides on top of them; see
[Reference priors](../../inference_io/discrete_pe_loader.md#reference-priors).

## Priors

Priors are NumPyro distributions specified in JSON. As with the model file, **keys are
regular expressions** matched against the parameter names the model asks for, and each
value is one of four things:

- a **dictionary** with a `dist` key naming any NumPyro distribution that takes scalar
  parameters, plus that distribution's arguments — this makes the parameter a free
  hyperparameter to be sampled;
- a **number**, which fixes the parameter to a constant;
- a **string**, which ties the parameter to another parameter so that both share a single
  sampled value;
- `null`, which passes `None` to the model (used for "no truncation on this side").

For example, $x \sim \mathcal{N}(2, 3)$ is written

```json
{
    "x": {
        "dist": "Normal",
        "loc": 2,
        "scale": 3
    }
}
```

The priors used in this example are

$$
\begin{align*}
    \ln\mathcal{R}_0 &\sim \mathrm{Unif}(0, 10) \\
    \alpha &\sim \mathrm{Unif}(-6, 6) \\
    \beta &\sim \mathrm{Unif}(-6, 6) \\
    m_{\mathrm{min}} &\sim \mathrm{Unif}(1, 20) \\
    m_{\mathrm{max}} &\sim \mathrm{Unif}(30, 80) \\
    \mu_{\chi_z} &\sim \mathrm{Unif}(-1, 1) \\
    \sigma_{\chi_z} &\sim \mathrm{Unif}(0, 1) \\
    \sigma_{\epsilon} &\sim \mathrm{Unif}(0, 1)
\end{align*}
$$

and their JSON representation lives in
[`prior_cfg.json`](https://github.com/kokabsc/gwkokab/blob/main/docs/source/examples/ecc_plus_spin/prior_cfg.json):

```json
{
    "log_rate_[0-9]+": {
        "dist": "Uniform",
        "high": 10.0,
        "low": 0.0
    },
    "alpha_pl_[0-9]+": {
        "dist": "Uniform",
        "high": 6.0,
        "low": -6.0
    },
    "beta_pl_[0-9]+": {
        "dist": "Uniform",
        "high": 6.0,
        "low": -6.0
    },
    "mmax_pl_[0-9]+": {
        "dist": "Uniform",
        "high": 80.0,
        "low": 30.0
    },
    "mmin_pl_[0-9]+": {
        "dist": "Uniform",
        "high": 20.0,
        "low": 1.0
    },
    "spin_1z_loc_pl_[0-9]+": {
        "dist": "Uniform",
        "high": 1.0,
        "low": -1.0
    },
    "spin_1z_scale_pl_[0-9]+": {
        "dist": "Uniform",
        "high": 1.0,
        "low": 0.0
    },
    "spin_2z_loc_pl_[0-9]+": "spin_1z_loc_pl_0",
    "spin_2z_scale_pl_[0-9]+": "spin_1z_scale_pl_0",
    "spin_[1-2]z_high_(pl|g)_[0-9]+": 1.0,
    "spin_[1-2]z_low_(pl|g)_[0-9]+": -1.0,
    "eccentricity_zeta_(pl|g)_[0-9]+": 0.0,
    "eccentricity_comp[1-2]_loc_(pl|g)_[0-9]+": 0.0,
    "eccentricity_comp1_scale_(pl|g)_[0-9]+": {
        "dist": "Uniform",
        "high": 1.0,
        "low": 0.0
    },
    "eccentricity_comp2_scale_(pl|g)_[0-9]+": 1.0,
    "eccentricity_comp[1-2]_high_(pl|g)_[0-9]+": null,
    "eccentricity_comp[1-2]_low_(pl|g)_[0-9]+": 0.0
}
```

Three things are worth pointing out.

- `spin_2z_loc_pl_[0-9]+` and `spin_2z_scale_pl_[0-9]+` are **strings**, tying the
  secondary spin distribution to the primary one. This encodes our modelling assumption
  that both black holes are drawn from the same spin distribution, and it means the
  sampler explores eight dimensions rather than ten.
- The eccentricity mixture is collapsed to a single component by fixing
  `eccentricity_zeta_...` to `0.0`. The parameters of the unreachable second component
  still have to be given values; they never enter the likelihood.
- Everything that is not a dictionary is a constant, and constants are written into the
  output file so that any post-processing step can reconstruct the model.

The eight free hyperparameters are sorted alphabetically internally, giving the ordering
that every downstream product uses:

```text
alpha_pl_0, beta_pl_0, eccentricity_comp1_scale_pl_0, log_rate_0,
mmax_pl_0, mmin_pl_0, spin_1z_loc_pl_0, spin_1z_scale_pl_0
```

which is $(\alpha, \beta, \sigma_\epsilon, \ln\mathcal{R}_0, m_{\mathrm{max}},
m_{\mathrm{min}}, \mu_{\chi_z}, \sigma_{\chi_z})$.

## Sampler Configurations

GWKokab ships two samplers, and which one runs is decided purely by the `sampler_name`
field of the sampler configuration file, so the analysis command is identical in the two
cases. Every field of both files — types, defaults, validation rules and what each knob
does — is documented in
[`SamplerConfig`](../../inference_io/sampler_config.md). This section covers only the
choices that are specific to *this* problem.

### NumPyro

The No U-Turn Sampler (NUTS) is configured with two sub-sections:
[`kernel`](../../inference_io/sampler_config.md#the-kernel-block) for the NUTS kernel and
[`mcmc`](../../inference_io/sampler_config.md#the-mcmc-block) for the MCMC driver. Our
[`discrete_numpyro/sampler_cfg.json`](https://github.com/kokabsc/gwkokab/blob/main/docs/source/examples/ecc_plus_spin/discrete_numpyro/sampler_cfg.json)
is

```json
{
    "kernel": {
        "step_size": 1.0,
        "inverse_mass_matrix": null,
        "adapt_step_size": true,
        "adapt_mass_matrix": true,
        "dense_mass": true,
        "target_accept_prob": 0.8,
        "max_tree_depth": 8,
        "find_heuristic_step_size": false,
        "forward_mode_differentiation": false,
        "regularize_mass_matrix": true
    },
    "mcmc": {
        "num_warmup": 5000,
        "num_samples": 7000,
        "num_chains": 4,
        "thinning": 1,
        "chain_method": "parallel",
        "progress_bar": true,
        "jit_model_args": true
    },
    "sampler_name": "numpyro"
}
```

Three of these choices are about this problem rather than about NUTS in general.
`dense_mass: true` matters most: several hyperparameters are strongly correlated (most
visibly $\alpha$ and $\beta$), and a diagonal mass matrix makes NUTS crawl through the
resulting ridge. `num_warmup: 5000` is long enough to adapt that full-rank matrix over
eight dimensions, and `num_chains: 4` is what makes $\hat{R}$ worth reading. The rest of
the file is at its default.

```{admonition} Chains and devices
:class: tip

`chain_method: "parallel"` maps the chains onto XLA devices, so on a single-CPU host only
one runs at a time. Either export `XLA_FLAGS=--xla_force_host_platform_device_count=4`
before the run, or switch to `"vectorized"`; see
[`chain_method` in detail](../../inference_io/sampler_config.md#chain_method-in-detail).
```

### flowMC

[flowMC](https://github.com/kazewong/flowMC) augments a local sampler with global
proposals drawn from a normalizing flow that is trained on the chains themselves. It
handles the correlated, curved posterior of this problem well, at the cost of more knobs —
[`FlowMCGlobalConfig`](../../inference_io/sampler_config.md#flowmc-flowmcglobalconfig)
documents each of them. Our
[`discrete_flowMC/sampler_cfg.json`](https://github.com/kokabsc/gwkokab/blob/main/docs/source/examples/ecc_plus_spin/discrete_flowMC/sampler_cfg.json)
is

```json
{
    "chain_batch_size": 0,
    "n_chains": 20,
    "batch_size": 5000,
    "history_window": 900,
    "n_epochs": 7,
    "n_max_examples": 100000,
    "n_NFproposal_batch_size": 10,
    "n_global_steps": 20,
    "n_local_steps": 300,
    "global_thinning": 1,
    "local_thinning": 1,
    "n_production_loops": 40,
    "n_training_loops": 30,
    "local_sampler_name": "hmc",
    "step_size": 0.01,
    "n_leapfrog": 10,
    "condition_matrix": [
        0.092886444,
        0.15304805,
        0.00029991572,
        0.038987259,
        3.7471383,
        0.18542411,
        0.0011376989,
        0.00084687465
    ],
    "learning_rate": 0.001,
    "rq_spline_hidden_units": [
        128,
        128
    ],
    "rq_spline_n_bins": 8,
    "rq_spline_n_layers": 10,
    "rq_spline_range": [
        -10.0,
        10.0
    ],
    "verbose": false,
    "sampler_name": "flowMC"
}
```

Two things are worth reading off this file. First the sample count: the run is
`n_training_loops` loops during which the flow is trained, followed by
`n_production_loops` loops that produce the posterior samples, and each loop performs
`n_local_steps` HMC steps followed by `n_global_steps` flow proposals. So 20 chains
$\times$ 40 production loops $\times$ 300 local steps give the 240 000 samples we end up
with.

Second, `condition_matrix` holds the variances of *this* posterior along each direction,
in the alphabetical hyperparameter order listed above. They span four orders of magnitude:
the posterior on $\sigma_\epsilon$ is about $0.017$ wide, while $m_{\mathrm{max}}$ is
constrained only to about $1.9\,M_\odot$. It is the one field that has to be measured
rather than guessed
([why](../../inference_io/sampler_config.md#condition_matrix-at-more-length)), and a short
pilot run followed by

```bash
gwk_diag_condition_matrix inference_data.hdf5
```

is what produced the numbers above.

## Running the Analysis

Both analyses use the same command, `discrete_n_pls_m_gs`, and differ only in which
`sampler_cfg.json` they point at. From
[`discrete_numpyro/analysis.sh`](https://github.com/kokabsc/gwkokab/blob/main/docs/source/examples/ecc_plus_spin/discrete_numpyro/analysis.sh):

```bash
XLA_PYTHON_CLIENT_ALLOCATOR=platform \
    XLA_PYTHON_CLIENT_PREALLOCATE=false \
    JAX_COMPILATION_CACHE_DIR="$HOME/jax_cache" \
    GWKOKAB_LOG_FILE="discrete.log" \
    discrete_n_pls_m_gs \
    --n-pl 1 \
    --n-g 0 \
    --seed $RANDOM \
    --n-buckets 4 \
    --data-loader-cfg "../data_loader_cfg.json" \
    --prior-cfg "../prior_cfg.json" \
    --pmean-cfg "../pmean_cfg.json" \
    --sampler-cfg "./sampler_cfg.json" \
    --add-truncated-normal-spin-z \
    --add-eccentricity-mixture

gwk_report -i inference_data.hdf5 -o discrete_numpyro_report.html
```

[`discrete_flowMC/analysis.sh`](https://github.com/kokabsc/gwkokab/blob/main/docs/source/examples/ecc_plus_spin/discrete_flowMC/analysis.sh)
is byte-for-byte the same except for the report name. Run each from its own directory:

```bash
cd discrete_numpyro && bash analysis.sh
cd ../discrete_flowMC && bash analysis.sh
```

The arguments are

- `--n-pl`, `--n-g`, `--add-truncated-normal-spin-z`, `--add-eccentricity-mixture` build
  the recovery model. **These must match the flags used to generate the data**, otherwise
  you are fitting a different model than the one that produced the catalogue.
- `--data-loader-cfg`, `--prior-cfg`, `--pmean-cfg`, `--sampler-cfg` point at the four
  configuration files above. Note that `--pmean-cfg` is the *same* file used for the
  injection campaign: the selection function must be identical on both sides, or the
  inferred rate will be biased.
- `--seed` seeds the sampler.
- `--n-buckets` is a memory/performance knob, explained below.

`JAX_COMPILATION_CACHE_DIR` is worth setting: the likelihood is a large JIT-compiled
graph, and caching it makes repeated runs start much faster.

### Buckets

Events do not all have the same number of posterior samples — the banana error model
discards samples that leave the physical region — but JAX prefers rectangular arrays
for better optimization. If all events were padded to the length of the longest one,
a lot of compute would be spent on padding.

Instead, GWKokab sorts events by sample count and partitions them into buckets using
Jenks' natural breaks, padding only within a bucket. `--n-buckets 4` asks for four
buckets. Leaving it out lets the CLI choose the number automatically, growing it until
the fraction of wasted (padded) space drops below `--threshold` (default `3.0` per cent).
More buckets mean less padding but more separate compiled kernels, so there is a sweet
spot; four works well here. A visualization on 69 BBH events from GWTC-3 is available in
[kokabs/gwkokab#568#issuecomment-3013176577](https://github.com/kokabsc/gwkokab/issues/568#issuecomment-3013176577).

### Output

Both samplers write `inference_data.hdf5` in the working directory.

For NumPyro:

```text
inference_data.hdf5
├── samples          # all chains concatenated, shape (num_chains * num_samples, 8)
├── chains
│   ├── chain_0      # per-chain samples, shape (num_samples, 8)
│   └── ...
├── constants        # attributes: every fixed model parameter
├── variables_index  # attributes: hyperparameter name -> column in `samples`
└── sampler_cfg      # attributes: the configuration actually used
```

For flowMC:

```text
inference_data.hdf5
├── samples          # local-sampler positions from the production loops
├── chains
│   ├── train        # per-chain positions and log-probabilities, training phase
│   └── prod         # ... and production phase
├── acceptances      # local/global acceptance rates, per phase
├── loss             # normalizing flow training loss
├── constants
├── variables_index
└── sampler_cfg
```

`variables_index` is what makes the output self-describing; note that both
`spin_1z_loc_pl_0` and `spin_2z_loc_pl_0` map to the same column, reflecting the prior
tie we set up earlier.

## Inspecting the Run

`gwk_report` renders a standalone HTML report from `inference_data.hdf5` — trace plots,
marginal and joint distributions, and convergence diagnostics — without needing the
original configuration files:

```bash
gwk_report -i inference_data.hdf5 -o discrete_numpyro_report.html
```

Beyond the report, the diagnostics to check and what to change in response depend on which
sampler ran:

- **NumPyro** — the $\hat{R}$ and effective sample size of the printed summary table; see
  [Reading the NumPyro diagnostics](../../inference_io/sampler_config.md#reading-the-numpyro-diagnostics).
- **flowMC** — the `loss` and `acceptances` datasets in the output file; see
  [Tuning a flowMC run](../../inference_io/sampler_config.md#tuning-a-flowmc-run).

For this data set both samplers converge comfortably, and the
[next tutorial](./inference_from_gaussian_summaries.md#comparing-the-methods) shows the
four runs agreeing with each other and with the injected truth.
